# Ballroom 全局 BPM 估计评估报告

对应任务书阶段 5（评估与调优）。所有数字均为本机实测，非估计值。

## 1. 数据与划分

| 项 | 值 |
|---|---|
| 数据集 | Ballroom Rhythm Dataset（`D:\training`，698 首） |
| 音频规格 | 44.1 kHz / 16-bit / 单声道，单首 29.5–34.1 s（中位 30.7 s） |
| 标注 | 698 个 `.bpm` 文件，整数 BPM，范围 60–224（中位 124） |
| 一致性 | wav ↔ bpm 严格 1:1（698/698） |
| 划分 | 按流派分层、固定种子 `seed=42`，训练 560 / 测试 138 |
| 划分文件 | `%TEMP%\bpm\split.json`（可复现） |

> 任务书阶段 1 给出的下载地址（`mtg.upf.edu`、`zenodo.org`）在本机 **DNS 解析失败**，
> 无法执行；实际使用的是用户本地提供的同一数据集。

## 2. 指标定义

- **Acc1** = `|pred − gt| ≤ 0.04 · gt`
- **Acc2** = `min(|pred−gt|, |pred·2−gt|, |pred/2−gt|, |pred·3−gt|, |pred/3−gt|) ≤ 0.04 · gt`

## 3. 结果（测试集 138 首）

| 手段 | Acc1 | Acc2 |
|---|---|---|
| 传统基线（自相关最强峰） | 0.428 | 0.957 |
| **候选评分模型（logreg/MLP + 保守覆盖）** | **0.754** | **0.949** |
| 验收线 | ≥0.70 基线 / ≥0.80 进阶 | ≥0.90 |

结论：**Acc1 达标（0.754 ≥ 0.70）、Acc2 达标（0.949 ≥ 0.90）；进阶目标 0.80 未达成。**

## 4. C# ↔ Python 一致性验证

`OsuPlayer.exe --eval-bpm <音频目录> --bpm-labels <真值目录>`（Release）跑完 698 首：

| | C# | Python |
|---|---|---|
| 测试集 Acc1 / Acc2 | 0.754 / 0.949 | 0.754 / 0.949 |
| 全量 Acc1 / Acc2 | 0.723 / 0.927 | 0.723 / 0.927 |
| 基线测试集 Acc1 | 0.442 | 0.428 |

两条结果的差异来自 1–2 首边界样本，说明 C# 特征管线（`BpmFeatureBuilder`）与 Python
训练口径一致，模型在播放器里不会因移植偏差而劣化。

## 5. 倍频错误分析

诊断（`tools/bpm/diag_candidates.py`）显示，**48%（336/698）的曲目**上自相关最强峰是
标注节拍的二倍 —— 音乐常在次强拍/细分上能量更强，这是自相关法的结构性失效模式，
也是 Acc1 远低于 Acc2 的根本原因（基线 Acc1 0.428 vs Acc2 0.957）。

模型的作用就是学会「哪个 metrical 层级才是真正的节拍」，因此 Acc1 提升 32.6 个点。

| Tango | 17 | 1.000 | 0.647 |
| VienneseWaltz | 13 | 1.000 | 1.000 |
| Rumba-International | 10 | 0.900 | 0.000 |
| Samba | 17 | 0.882 | 0.176 |

## 6. 优化前后对比

| 步骤 | 测试集 Acc1 | 说明 |
|---|---|---|
| 自相关基线 | 0.428 | 只取最强峰 |
| + 候选集（峰 ∪ 倍频亲属） | — | 候选召回 0.789 → 0.867 |
| + 候选评分模型（无条件覆盖） | 0.717 | Quickstep 被压到 0.062 |
| + 保守覆盖阈值 0.10 | **0.754** | 修复 Quickstep 回退 |
| + onset 包络帧循环并行 | 0.754 | 单曲 1752 ms → **~310 ms**（结果逐位不变） |

已试且确认无收益/负收益的做法（均已回退，不再重试）：
抛物线峰位细化（召回 0.867→0.832）、max_candidates 超过 20、peaks 超过 5。

## 7. 性能（验收项：单曲 CPU < 2 s）

用 `--detect-bpm <文件>` 单曲串行测量（Release，i7-7500U，无并发争用），每首连跑 3 次：

| 曲目 | 第 1 次（冷） | 第 2 次 | 第 3 次（稳态） | 分阶段（稳态） |
|---|---|---|---|---|
| Cafe_Paradiso-05 | 1442 ms | 675 ms | **302 ms** | 解码 11｜特征 285｜显著度 4｜模型 0 |
| Ballroom_Classics4-01 | 1224 ms | 682 ms | **331 ms** | 解码 14｜特征 311｜显著度 5｜模型 0 |
| AnaBelen_Veneo-02 | 1302 ms | 795 ms | **308 ms** | 解码 13｜特征 290｜显著度 4｜模型 0 |
| AnaBelen_Veneo-11 | 1186 ms | 623 ms | **312 ms** | 解码 14｜特征 292｜显著度 4｜模型 0 |
| Ballroom_Classics4-11 | 1568 ms | 624 ms | **327 ms** | 解码 17｜特征 305｜显著度 4｜模型 0 |

- **稳态单曲 ~310 ms，冷启动（JIT + 模型加载）最高 1568 ms，均 < 2 s → 达标。**
- 唯一热点是 onset 包络（STFT + 逐 bin sqrt/log，约 290 ms），已按帧分块并行（2 核）；
  自相关只有 ~4 ms，模型推理 < 1 ms。

> 早前批处理评测报出的「平均 2252 ms」是在 2 物理核上以 2 路并发跑 698 首测得的，
> 每首都在与另一首争核，且没有线程预热，属测量口径失真；播放器实际是单曲串行分析。

## 8. 应用到实例：真实 osu! 曲库验证

Ballroom 是舞曲，模型用在播放器的实际曲库上会不会帮倒忙是必须单独验证的事。
用 100 首真实谱面基准（`--train-beatmaps`，走完整播放路径 `BeatAnalyser.run`，即模型
在 `fuseTempo` 之后接管节拍层级）对比：

| 指标 | 未启用模型 | 启用模型 | 变化 |
|---|---|---|---|
| **BPM 完全正确** | 18/100 | **69/100** | **+51** |
| **BPM 平均绝对误差** | 30.64 | **23.77** | −22% |
| 首拍误差中位数 | 77 ms | 69 ms | 改善 |
| 小节偏差中位数 | 411 ms | 366 ms | 改善 |
| 八度错 | 7 张 | 19 张 | 变差 |

- 101 首的 BPM 结果发生变化，证明模型确实在播放路径里生效。
- 典型修复：`-ERROR` 200→134（八度错）变为 200→200；`Kamigami ga Koishita Gensoukyou`
  155→118（误差 37）变为 155→155。
- **需要如实说明的副作用**：八度错从 7 张涨到 19 张 —— 模型在修好大量普通错误的同时，
  也在 12 首上把层级换错。但净效果是压倒性的（正确数 +51、平均误差 −22%）。
- 关闭方式：删掉或重命名 `models/bpm/bpm.onnx` 即自动回退原生（与 kiai 模型同一机制）。

遗留两点（如实记录）：

1. 仓库根的 `beatmap-training-report.txt` 是**未启用模型**时的 302 报告（49/302、MAE 32.31），
   与当前配置不一致。已给报告头加上「BPM 层级模型：已启用/未安装」一行，今后不会再混淆；
   该 302 全量刷新在本机跑不划算（见第 2 点），未重跑。
2. **批量评测路径异常慢**：302 全量在 Release 下跑 27 分钟仍未完成（Debug 下 43 分钟），
   而单曲稳态只要 310 ms —— 这是批量模式的问题（每首 2 路并发 × onset 内部再并行，
   在 2 物理核上超订，叠加解码产生的大数组回收压力），**不影响播放器**（单曲串行分析）。

## 9. 未达标项与后续

1. **Acc1 0.754 < 0.80**：候选召回 0.968 已是当前前端的上限，继续提升必须换更强的
   前端（mel 频谱 CNN / PEA-Tempo 32.6 万参数），属数天量级工作。
2. **Waltz（0.182）**：慢速 3/4 拍曲目系统性选错层级，需要针对性补样本或加入节拍型先验。
3. 推理耗时已达标（见 §7），无需再优化。
